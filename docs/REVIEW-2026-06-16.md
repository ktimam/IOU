# IOU — Code Review (2026-06-16)

> Advisory review. **No code or existing docs were changed** to produce this file.
> Scope: how IOU compares to its generic sibling **ICTemplate** on shared functionality,
> divergences/bugs, and test coverage. Security vulnerabilities are covered in depth in the
> companion memo **[SECURITY-MEMO-2026-06-16.md](SECURITY-MEMO-2026-06-16.md)** — read that next.
> Reviewer: automated multi-agent audit + manual verification of every high-severity finding.

## TL;DR

IOU is a feature-rich, mostly well-built app with genuinely reusable patterns (recovery
mnemonic, offline Ed25519 signing, CSV export, in-memory key sessions, scoped vetkd). But on
**shared infrastructure the generic template now gets several things right that IOU does not**,
and IOU carries **real security/correctness bugs** (covered in the security memo). The most
serious is that **IOU has no stable storage and no upgrade hooks** — an in-place canister
upgrade wipes all data, despite comments claiming otherwise.

## What's done well

- **Rich, correct backend authorization.** Every read and write checks pair/sheet membership
  (`caller_is_pair_member`, `is_member_of`); `edit_entry` enforces creator-only mutation;
  reads are not trusted just because they're queries.
- **`inspect_message` hook is well-designed** — explicit whitelist + anonymous-trap for writes +
  explicit `accept_message()`. I verified **all 24 service methods are whitelisted** (no
  missing-method trap) and the v1.2.3 `accept_message` fix is in place.
- **Consistent input validation** — ISO-4217 currency codes (3 ASCII letters), `closing_window_days`
  bounds (30..=730), 16-currency cap, fixed-length crypto material (32/64-byte checks).
- **Domain-separated Ed25519 verification** (`canonical_replace_bytes` with `iou-replace-member-v1:`
  prefix + `0xff` separators) — good discipline (with caveats in the security memo).
- **Strong client key hygiene** — `K_sheet` and derived keys held in memory only
  (`SheetKeyContext`), private keys imported non-extractable where possible.
- **prodVetkd is correct** — uses `DerivedPublicKey.deserialize(masterPubKey)` directly (no
  client-side re-derivation); G1 transport key. This matches the template (both fixed it).

## Divergences vs ICTemplate — where IOU is BEHIND (adopt template → IOU)

These are shared-functionality items where the template is the correct reference:

## Test coverage gap

- **Backend has 0 `cargo` unit tests.** The template ships 2 (error-code stability + Candid
  round-trip). At minimum, pin the error-code/method contract and add tests for the pure
  validation paths (currency ISO check, `closing_window_days` bounds, length checks).
- IOU lacks the template's `unwrap.ts` Candid helper + its 11 tests. Frontend vitest coverage
  (25 tests) is otherwise good and broader than the template's.

## Reusable strengths IOU HAS that the template should take (IOU → template)

These are clean, domain-free, and worth extracting upstream:

- **`recovery/mnemonic.ts`** — 24-word BIP-39 (`@scure/bip39`), validate/generate/seed, IndexedDB
  persistence with Node no-op fallback. Wire `seedFromMnemonic()` as the deterministic seed for
  the transport/dev keypair so recovery is real.
- **`replaceMember/replaceMember.ts`** — offline Ed25519 sign + QR handoff with canonical bytes
  (domain prefix + `0xff` separators) byte-matching the canister. (Fix the principal-binding gap
  first — see security memo.)
- **`entries/csvExport.ts`** — extract the generic `escapeCsvCell` (RFC-4180) + `downloadCsv`
  (Blob + revoke) helpers; leave the IOU column mapping behind.
- **`flows/SheetKeyContext.tsx`** — in-memory per-resource key cache that routes dev/prod vetkd
  behind `isProdVetkd()`. Generalize to `ResourceKeyContext`.
- **`AuthCtx.identity` accessor** (v1.1.5) — ergonomic identity access the template lacks.

> ⚠️ When porting these, do **not** carry IOU's plaintext-secret-at-rest behavior (mnemonic in
> IndexedDB, Ed25519 seed JSON in localStorage). Route through `mobileSecureStorage` on native or
> encrypt on web.

**Reference-only (IOU domain-specific, don't copy wholesale):** `entries/balance.ts`,
`entries/fx.ts` (hardcoded frankfurter.app), `entriesToCsv()`/`COLUMNS`, `SetDisplayName.tsx`.

## Multi-replica note

IOU uses the dfx default **port 4943** with `.dfx` in the repo and the global `default` identity —
so it **collides with the template** (also 4943) when both run locally. Adopt the per-project
port/state/identity scheme described in the template's review (generalized from Soccer's
`scripts/dfx_start.sh`, which runs isolated on 40435).
